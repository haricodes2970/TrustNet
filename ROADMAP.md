## Workspace Module — Phase 1 (Backend Developer 2)

Model, CRUD, membership projection, and permission resolution implemented — foundation for future Projects/Tasks/Milestones/Documents modules. `Workspace.startup` is unique (DB-enforced, exactly one workspace per startup). Access resolved live via `resolveWorkspaceAccess` against `Startup.founder` (owner tier) and `Team.members` (admin/contributor tiers, queried directly against the `Team` model — no `teamService` coupling, by explicit design decision). No invite/membership-mutation endpoints on Workspace — reuses existing Team invite flow. Projects/Tasks/Milestones/Documents are explicitly out of scope for this phase. Full detail: [docs/modules/workspace.md](docs/modules/workspace.md).

## Projects Module — Sprint 1 Phase 2 (Backend Developer 2)

Project container built on top of Workspace: model, CRUD, permission enforcement. All authorization derives exclusively from `workspaceService.resolveWorkspaceAccess()` — `Project.owner` (creator) and `Project.status` (business lifecycle) are explicitly never consulted for permissions, audit/business fields only. `updatedBy` added for audit trail on every mutation. Caught and fixed a permission-bypass risk during implementation: `listProjectsForUser` now re-verifies access on an explicit `?workspaceId=` filter instead of trusting it. No modifications to Startup/Team/Workspace modules. Tasks/Milestones/Documents remain out of scope. Full detail: [docs/modules/projects.md](docs/modules/projects.md).

## Tasks Module — Sprint 1 Phase 3 (Backend Developer 2)

Task container built on top of Project (no denormalized Workspace ref — resolved through Project on every check, deliberate choice). First module granting non-owner/admin write access: `canMutateTask()` (new pure helper in `serviceUtils.js`, unit-tested, reusable by future collaboration modules) composes with `workspaceService.resolveWorkspaceAccess()` — contributors may mutate only tasks they created or are assigned to; owner/admin unrestricted. `assignedTo` validated against `listWorkspaceMembers`; contributors may only self-assign. No modifications to Startup/Team/Workspace/Project modules. Milestones/Documents remain out of scope. Full detail: [docs/modules/tasks.md](docs/modules/tasks.md).

## Milestones Module — Sprint 1 Phase 4 (Backend Developer 2)

Milestone container built on top of Project — structural planning entity, owner/admin-only permissions (contributors participate through Tasks, not Milestones), resolved via the same `workspaceService.resolveWorkspaceAccess()` mechanism Project already uses. First phase requiring a Task-module change: `Task.milestone` (nullable ref, **update-only** — not settable at creation, workflow is create-task-then-assign), with an integrity check ensuring the milestone belongs to the task's project. Task's existing permission logic (`canMutateTask`) untouched. Full existing test suite re-verified passing after the Task edits — no regression. No modifications to Startup/Team/Workspace/Project. Documents remains out of scope. Full detail: [docs/modules/milestones.md](docs/modules/milestones.md).

## Documents Module (Backend Developer 2)

Document upload/metadata/access-control built on top of Project (`Workspace → Project → Document`, never attached to Workspace or Task directly, per explicit design decision). New `storageService.js` abstraction (`upload`/`downloadUrl`/`remove`) with a local-disk default provider — no external provider chosen this phase, same "most appropriate equivalent without inventing infra" reasoning as the `node --test`/`mongodb-memory-server` calls in the two prior infrastructure phases. No delivery URL is ever persisted — generated on demand on every read. New dedicated `canMutateDocument()` helper (explicitly not a reuse of `canMutateTask()`, per instruction) — owner/admin manage any document, contributor may only mutate documents they uploaded. 20 new integration tests (reusing the existing `createCollaborationFixture()`, no new fixture) + 11 new unit tests, all passing (112/112 combined with pre-existing suite). One test-authoring mistake caught and fixed during development (archived-workspace vs archived-project guard confusion) — not a production bug, documented in [docs/modules/documents.md](docs/modules/documents.md). No modifications to Startup/Team/Workspace/Project/Task/Milestone. Versioning, previews, OCR, comments, folders, collaborative editing, and sharing explicitly out of scope. Full detail: [docs/modules/documents.md](docs/modules/documents.md).

## Hiring Module (Backend Developer 2)

Job postings built directly on Startup — no Workspace/Project/Documents dependency, first module with a genuinely public (unauthenticated) read surface. `jobService.js` implements its own `resolveStartupAccess()`/`getAccessibleStartupIds()`, a **deliberate, explicitly-instructed duplication** of `workspaceService.resolveWorkspaceAccess()`'s role logic — not extracted into a shared primitive, since the collaboration permission layer is already integration-tested and stays untouched until a dedicated future refactoring phase. Owner/admin manage jobs fully; contributors read-only (draft and published); public sees published-and-non-archived only, with unpublished jobs returning 404 (not 403) to conceal existence. List endpoint uses a "downgrade to public subset" pattern for unauthorized filters, not outright rejection — a different shape than every prior module's list-filter fix. New `createStartupTeamFixture()` test helper proves Workspace/Project independence by construction. 27 new integration tests + 11 new unit tests, 150/150 combined passing. No modifications to Startup/Team/Workspace/Project/Task/Milestone/Document. Full detail: [docs/modules/hiring.md](docs/modules/hiring.md).

## Applications Module (Backend Developer 2)

Job applications built on Hiring (`Startup → Job → Application`), reusing `jobService`/`storageService` directly — no `Document` model/`documentService`, no new duplicated Startup-authority logic (unlike Hiring, Applications correctly reuses `jobService.resolveStartupAccess` rather than reimplementing it a third time). First module with a third distinct authority shape: flat candidate-ownership (`applicant === userId`, no role resolution) alongside the reused owner/admin tier — contributor gets explicitly zero access (not read-only, unlike Job's contributor tier), and there's no public tier at all. First module with per-viewer field redaction (`notes` hidden from the candidate). Status lifecycle enforced by a pure, unit-tested state machine (`assertValidStatusTransition`) — no skip-ahead, staff-reject-from-anywhere, candidate-withdraw-from-anywhere, terminal states immutable. Duplicate-application prevention via both an app-level check and a DB-level partial unique index (`{job,applicant}`, excluding `withdrawn`). Dedicated `PUT /:id/resume` and `PUT /:id/cover-letter` endpoints replace a generic update, per instruction. One test-infra concurrency bug found and fixed (shared local-storage-directory cleanup race between this module's and Documents' integration tests under `npm run test:all`) — not a production bug, verified stable across repeated full-suite runs. 28 new integration tests + 12 new unit tests, 190/190 combined passing. No modifications to Startup/Team/Workspace/Project/Task/Milestone/Documents/Job service files. Full detail: [docs/modules/applications.md](docs/modules/applications.md).

## Investor Module (Backend Developer 2)

`InvestorProfile` (public directory, User-owned, no Startup relationship) and `InvestmentInterest` (`Investor → InvestmentInterest → Startup`) — two independent resources, not nested under Workspace/Project or under Hiring. `investmentInterestService.js` implements its own `resolveStartupAccess()` — a **third, deliberate duplication** of the role-computation logic already in `workspaceService.resolveWorkspaceAccess()` and `jobService.resolveStartupAccess()`, an explicit instruction for this phase, not an oversight (`workspaceService.js`/`jobService.js` both left untouched). Contributor gets **read-only** access to interests for their startup — the deliberate divergence from Applications, where contributor got zero access. No public tier on `investment-interests` (every route authenticated), unlike `investors` (public list/get) and unlike Job. Status lifecycle enforced by a pure, unit-tested state machine (`assertValidInterestTransition`) — same shape as Applications, kept separate per the project's "structurally similar but deliberately not shared" convention. Duplicate-interest prevention via app-level check + DB-level partial unique index (`{startup,investor}`, excluding `withdrawn`). Draft implementation was reviewed against architecture before completion; the primary adjustment was adopting typed `ApiError` with explicit status codes (400 validation/404 not-found/403 authorization/409 conflict) in both services, replacing plain `Error` throws, matching the convention used by Applications/Documents/Task/Project/Workspace/Team/Startup controllers — controllers are now pure pass-through with no per-route hardcoded status guessing. 29 new integration tests (including a dedicated ApiError status-code contract block) + 10 new unit tests, 235/235 combined passing. No modifications to Startup/Team/Workspace/Project/Task/Milestone/Documents/Job/Application service files. Full detail: [docs/modules/investors.md](docs/modules/investors.md).

## Funding Module (Backend Developer 2)

`FundingRound` (`Startup → FundingRound`) and `FundingContribution` (`FundingRound → FundingContribution`), independent of Workspace/Project and independent of Investor (`InvestorProfile`/`InvestmentInterest` — a contribution references `User` directly, no forced coupling to a profile). `fundingRoundService.js` implements its own `resolveStartupAccess()` — a **fourth, deliberate duplication** of the role-computation logic already in `workspaceService`/`jobService`/`investmentInterestService`, an explicit instruction for this phase (none of the three prior files touched). Contributor gets read-only access on both resources, same tier Investment Interest established. `FundingRound` reuses Job's 404-concealment convention for non-open/archived rounds (existence hidden from unauthorized viewers, not just content) — the first reuse of that specific precedent outside Hiring itself. Two independent lifecycle state machines (`assertValidRoundTransition`, `assertValidContributionTransition`), both pure and unit-tested, deliberately not shared with each other or any prior module's transition helper. **Funding totals**: confirming a contribution atomically `$inc`s both `FundingRound.raisedAmount` and the pre-existing (previously unused) `Startup.fundingRaised` field — the first module to write to a `Startup` field it doesn't otherwise own, and the first use of a `findOneAndUpdate` status-filter as a race guard around a financial side effect in this codebase. Typed `ApiError` (400/403/404/409) used throughout, matching the convention established in the Investor phase — no plain `Error` throws. 46 new integration tests (including a dedicated funding-totals verification block: single-confirm, cumulative-multi-confirm, and pledged/rejected/withdrawn-leave-totals-untouched) + 18 new unit tests, 299/299 combined passing. No modifications to Startup/Team/Workspace/Project/Task/Milestone/Documents/Job/Application/Investor service files. Full detail: [docs/modules/funding.md](docs/modules/funding.md).

## Marketplace Module (Backend Developer 2)

`ProviderProfile` (`User → ProviderProfile`, public directory, flat ownership, no Startup relationship), `ServiceListing` (`ProviderProfile → ServiceListing`, draft/published/archived lifecycle mirroring Job's shape), `EngagementRequest` (`Startup → EngagementRequest ← ServiceListing`, the first resource in this codebase requiring two independent authority mechanisms simultaneously — Startup-role for the requester, flat provider ownership for the fulfiller). `engagementRequestService.js` implements its own `resolveStartupAccess()` — a **fifth, deliberate duplication** of the role logic in `workspaceService`/`jobService`/`investmentInterestService`/`fundingRoundService`, an explicit instruction for this phase (none of the four prior files touched). Providers are individual Users, not Startups, by design — avoiding a sixth duplication on the supply side. `ServiceListing.provider` deliberately refs `ProviderProfile` (not `User` directly), a considered divergence from Funding/Investor's deliberate profile/contribution decoupling. Reuses Job's/FundingRound's 404-existence-concealment convention for non-published/archived listings. `assertValidEngagementTransition` — the most complex transition table of any module so far (two actors, two non-terminal exit points), pure and unit-tested, deliberately not shared with any prior transition helper. Partial unique index on `{serviceListing, startup}` excludes three terminal statuses (wider than any prior duplicate-prevention index), permitting re-engagement after any terminal outcome including a successful completion. Typed `ApiError` (400/403/404/409) used throughout. 60+ new integration tests (including explicit coverage for cross-provider/cross-startup isolation and re-engagement-after-each-terminal-state) + 30 new unit tests, 369/369 combined passing. No modifications to Startup/Team/Workspace/Project/Task/Milestone/Documents/Job/Application/Investor/Funding service files. Full detail: [docs/modules/marketplace.md](docs/modules/marketplace.md).

## Analytics Module (Backend Developer 2)

Read-only cross-domain analytics layer — no model of its own, no write operations anywhere, the first fully read-only module in this codebase. `analyticsService.js` reads `Startup`/`Workspace`/`Project`/`Task`/`Milestone`/`Job`/`Application`/`InvestmentInterest`/`FundingRound`/`FundingContribution`/`ServiceListing`/`EngagementRequest`/`Team` directly via `find()`/`countDocuments()`/`aggregate()`. Own local `resolveStartupAccess()` — a **sixth, deliberate duplication** of the role logic in `workspaceService`/`jobService`/`investmentInterestService`/`fundingRoundService`/`engagementRequestService`, deferred again per explicit instruction. Six endpoints under `/api/v1/analytics` (`overview`/`projects`/`tasks`/`hiring`/`funding`/`marketplace`, `?startupId=` query param, any-role gate — the simplest permission model of any module, a direct consequence of being read-only). No admin/platform-wide analytics surface, out of scope per explicit decision — every metric scoped to one Startup the caller has a role on. No new persistent model — computed on demand, an `AnalyticsSnapshot`-style cache/rollup deferred to `BACKLOG.md` for if/when query volume or trend-data needs justify it. New pure `defaultCounts()` helper (unit-tested) fills every known status enum with 0 so zero-activity Startups return real zeros, not sparse objects. 13 new integration tests (including exact-count correctness against a known cross-domain seed, and an overview-vs-dedicated-endpoint no-drift check) + 4 new unit tests, 386/386 combined passing. No modifications to any prior module's service files. Full detail: [docs/modules/analytics.md](docs/modules/analytics.md).

## Reports Module (Backend Developer 2)

Presentation/export layer over Analytics — no model of its own, no domain-model queries anywhere in `reportService.js`. Every report type (`startup`/`projects`/`tasks`/`hiring`/`funding`/`marketplace`) dispatches through a lookup table directly to the corresponding existing `analyticsService` function; Reports adds only export-format serialization and a thin envelope. **No seventh Startup authorization helper** — reuses `analyticsService.resolveStartupAccess`/`assertAnyRole` directly, narrowed to owner/admin only via a thin local `assertOwnerOrAdmin` wrapper. Contributor excluded (403) — a deliberate, instructed divergence from Analytics' any-role gate, the first time this codebase restricts a *read* action below contributor tier; directly tested alongside a companion test confirming the same contributor can still read the identical data via Analytics itself. Two export formats: JSON (envelope passthrough) and hand-rolled CSV (`flattenToRows`/`escapeCsvField`/`toCsv`, pure and unit-tested, RFC 4180 escaping, no new dependency) — **PDF explicitly not implemented this phase**, recorded in `BACKLOG.md` with library options for a future phase. `format=csv` is the first response in this codebase to bypass the `{success,data}` envelope (file-download `Content-Disposition`). One route (`GET /api/v1/reports/:reportType`) rather than six. 14 new integration tests (including JSON-matches-Analytics-exactly no-drift checks and CSV comma-escaping end-to-end) + 9 new unit tests, 409/409 combined passing. No modifications to any prior module's service files, including `analyticsService.js` itself. Full detail: [docs/modules/reports.md](docs/modules/reports.md).

## AI Module (Backend Developer 2) — final roadmap item

Thin orchestration layer over Analytics/Reports/domain services — no model, no persistence of any kind (no conversations, no embeddings, no vector store, no RAG, no agent framework, no workflow engine), fully stateless except an in-memory (non-persisted) per-user rate-limit counter. `aiService.js` performs **zero authorization of its own** — no `resolveStartupAccess()` at all, the first Startup-adjacent module in the entire roadmap to introduce none: every one of the eight capabilities (`startup-summary`/`project-progress`/`task-prioritization`/`hiring-insights`/`funding-summary`/`marketplace-recommendations`/`analytics-interpretation`/`report-explanation`) dispatches to an existing `analyticsService`/`reportService`/`taskService`/`serviceListingService` function and inherits that function's authorization unmodified — directly proven by `report-explanation` correctly denying contributor (403, inherited from Reports' stricter gate) while every other capability allows contributor (inherited from Analytics' any-role gate). One narrow, documented normalization: `taskService`'s pre-`ApiError`-convention plain `Error` on unauthorized task access is caught and re-typed to `ApiError(403)` without re-deriving the decision. Exactly one provider abstraction (`aiProviderService.generateCompletion()`), backed by a deterministic no-network default (same "most appropriate equivalent without inventing infra" reasoning as `storageService`'s local-disk provider) — a real LLM provider is an explicitly deferred decision, tracked in `BACKLOG.md` with named options, same treatment PDF export received in Reports. Deterministic three-part prompt construction (system prompt → structured context → user question), pure and unit-tested. Provider failures map to the codebase's first `502` responses; rate-limit exhaustion maps to its first `429`s. `POST /api/v1/ai/insights` — capability lives in the request body (not a path param, to support Joi's conditional `.when()` validation against sibling fields) — the first new Joi validator file since Marketplace. 16 new integration tests (including authorization-inheritance-per-capability, a monkey-patched provider-failure test, and per-user rate-limit isolation) + 14 new unit tests, 439/439 combined passing. No modifications to any prior module's service files, including `analyticsService.js`/`reportService.js`/`taskService.js` themselves. Full detail: [docs/modules/ai.md](docs/modules/ai.md).

## Backend Merge (post-roadmap hardening)

With the roadmap complete (Authentication through AI), an independently-developed TrustNet backend ("Developer 1") was compared against this one for a possible merge. Developer 1 had zero automated tests and a structurally different domain model (its own social graph, admin/audit, realtime, background-job, and AI-gateway subsystems, plus `StartupMember`/`StartupInvitation` in place of `Team`/`Workspace`) — none of it on this roadmap. Decision: keep this backend's architecture wholesale; adopt only two self-contained pieces that closed standing Phase 1 gaps — `sanitizer` middleware (NoSQL-injection/XSS-at-the-edge defense, fixed for Express 5's getter-only `req.query`) and `rateLimiter`/`rateLimits` (`express-rate-limit`-based, IPv6 key-generation fixed, `auditLogService` coupling dropped since that model wasn't adopted). Full detail: `BACKLOG.md` "Backend merge" section.
